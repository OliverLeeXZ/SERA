# Dataset

This is the single data root used by Training and Evaluation. Data is bundled;
generation is optional and does not run automatically during training/evaluation.

```
Dataset/
  training/
    textcraft_synth_train.jsonl                  # 2,522 (852 medium used for training)
    textworld_train.jsonl                        # 1,500
    textworld_multidish_train_1500_v9.json
  validation/
    textcraft_synth_val.jsonl                    # 632 validation-pool tasks
    textworld_dev.jsonl                          # 200 (50 per difficulty)
    textworld_multidish_validation_200_v9.json
  eval/
    textcraft_synth_val.jsonl                    # 632 full-evaluation payloads
    textcraft_synth_val_all_632.json              # fixed evaluation index
    textworld_test.jsonl                         # 1,400 full task specifications
    textworld_multidish_test_1400_v9.json
  generation/
    generate_textworld.py                        # the only generation entry point
    cooking_tasks.py                            # recipe/family construction
    parameter_sampling.py                       # seeded difficulty/runtime sampling
    textworld_v9.json                            # generation config
    cooking_world.json                          # source food/preparation database
    licenses/textworldexpress-Apache-2.0.txt
```

Each split is flat: environment-prefixed files live directly inside it, with no
`textcraft/` or `textworld/` subdirectories. Training and evaluation use the same
central path resolver; already-prefixed names are not prefixed twice.

The TextCraft validation and evaluation payloads contain the same 632 tasks.
Training constructs a 100-task subset from this pool, with periodic validation
disabled by default; full evaluation uses all 632. These are not independent
development and test splits.
TextWorld has separate generated train/dev/test folds, with training difficulty
counts Medium=900, Hard=150, Extreme=450 and evaluation counts 350 per difficulty.

## Generate TextWorld data

The generator uses the Python standard library on Linux and the bundled
CookingWorld database; no model or GPU is required.
From the repository root:

```bash
# Built-in data already exists. Explicitly regenerate the three TextWorld splits:
python Dataset/generation/generate_textworld.py --overwrite

# Generate a separate dataset; programs can immediately consume it via this root:
python Dataset/generation/generate_textworld.py --dataset-root /shared/new-dataset
export SERA_DATASET_ROOT=/shared/new-dataset

# Generate only selected splits; leave all other files unchanged:
python Dataset/generation/generate_textworld.py --splits training validation --overwrite
```

Without `--dataset-root`, output goes directly to this root's `training/`,
`validation/` and `eval/` folders, with `textworld_` filename prefixes. It writes
one JSONL plus one manifest per split. **Existing files require `--overwrite`**;
TextCraft data is never touched. Stop active runs before regenerating their data.
An alternative root generated by this command contains TextWorld only; copy the
`textcraft_*` files into the corresponding splits there as well if you also
want to run TextCraft from it.

Use `--config /path/to/config.json` for another generation config, or `--source-db`
for another CookingWorld database. The config's relative database path resolves
against the config directory, not the current working directory. Commands work
from any directory when the script is invoked by its absolute path.

The generator uses deterministic seeds and split-specific difficulty quotas.
The test matrix contains seven task families × four difficulties × 50 tasks.
Recipe construction includes compatible preparation sampling, dependency
gates, and shared-resource constraints. See
[Evaluation/TextWorld/README.md](../Evaluation/TextWorld/README.md)
for task-family and difficulty-band details.

Generated task files are atomically replaced individually after all requested
splits are generated and validated. Manifests record JSONL, source database and
configuration hashes. Task records use split names `train`, `dev`, and
`test`/`validation`. Restart processes after regeneration to
clear in-memory dataset caches. Existing evaluation plans pin manifest hashes;
make a new run directory if data changed.
